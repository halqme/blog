AIコーディングエージェントを使い続けていると、モデルの賢さだけでは解決しにくい失敗に何度も出会います。
調査が不十分なまま編集を始める。最初に作った計画が外れているのに、そのまま消化する。テストを実行せず「確認済み」と判断する。別のエージェントの報告を検証せず受け入れる。

こうした失敗を減らすために、最初はプロンプトと便利なツールを足していました。しかし、機能を増やすほどエージェントが安定するわけではありませんでした。むしろ、似た道具や重複した指示が増え、モデルが「どれを、いつ使うか」を判断する負担も大きくなります。

そこで、守ってほしい手順を文章で増やすのではなく、失敗してはいけない境界を実行時の仕組みに移すために[halqme/pi-kit](https://github.com/halqme/pi-kit)を作っています。

## Pi Kitの全体像

Pi Kitは、[Pi Coding Agent](https://github.com/earendil-works/pi)へ開発支援機能を追加するPi packageです。TypeScriptで実装したextension、必要なときだけ読み込むskill、短いprompt templateを一つのリポジトリにまとめています。

現在の構成は、大きく三つに分かれます。

```text
Pi Kit
├── 開発作業の中核
│   ├── repository ── 調査するcontext / 変更するcode
│   ├── task ──────── 目標を保持するtask / 証拠を扱うverify
│   └── delegate ──── 別worktreeで子Piを動かす
│
├── 実作業を支える汎用utility
│   ├── terminal / background-process
│   ├── browser-inspector
│   └── session-metrics
│
└── 必要な場面だけ読み込む知識
    ├── skills
    └── prompts
```

一番上の「開発作業の中核」は、調査、変更、完了判定、委譲に対して、モデルが越える境界を決めます。その下のutilityは、ターミナルやブラウザなど実際の作業場所を提供します。skillとpromptは、問題の診断や安全な操作、テスト設計といった進め方を補います。

つまり、個々のツールを寄せ集めただけではありません。**壊すと困る部分はextensionで機械的に制約し、状況によって変わる進め方はskillへ分ける**のが、現在のPi Kitの構成です。

ただ、最初からこの形を狙っていたわけではありません。

## 最初は「便利なものをまとめたパッケージ」だった

Pi Kitの最初のcommitは2026年7月31日です。当時のREADMEでは、プロジェクトを次のように説明していました。

> A collection of Pi extensions and reusable agent skills for planning, collaboration, background work, and project-aware automation.

実際、初期の中心は三つのextensionでした。複数のPiで議論やレビューを行う`agent-team`、長時間のコマンドを扱う`background-process`、実装前に計画をレビューする`grill-plan`です。

この段階のPi Kitは、普段の開発で欲しくなった機能を一つのpackageから導入できるようにする「便利なもの置き場」に近いものでした。目的は分かりやすい一方、各機能が一つの設計原則でつながっていたわけではありません。

8月に入ると、実際のセッションで見つかった不便を埋める形で機能が急速に増えます。

- 構文を調べて安全に編集する`Astrolabe`
- リポジトリを字句検索する`bm25_search`
- 計画を扱う`plan`、`planner`、`grill`
- 作業継続を制御する`runner`と`loop`
- セッションをまたぐ`threads`、のちの`pi-intercom`
- 複数エージェントを動かす`Herdr`連携や`agent_team`
- モデルへ作業方針を繰り返し注入する`inception`
- 利用状況を調べる`session_metrics`

それぞれには追加した理由がありました。たとえばAstrolabeには、複数言語対応、編集対象を表すhandle、LSPを使ったrename、往復回数を減らすbatch inspectionが順に加わっています。`session_metrics`も単なる集計から始まり、cache利用、tool action、現在のPiログ形式への対応へ広がりました。

一方で、Git履歴を見ると、追加と同じくらい置き換えも発生しています。Herdr連携は導入から数日で削除され、terminalはHerdr依存からtmuxへ移行しました。`threads`は`pi-intercom`へ置き換わり、さらに後の再設計で外部依存ごと外れています。計画と継続制御の周辺には、役割の近いextensionとskillがいくつも存在していました。

個々の変更が間違っていたというより、セッションで見つかった問題に対して、その都度新しい機能や指示を追加していたためです。その結果、できることは増えましたが、Pi Kit全体として何を保証するのかは説明しにくくなっていきました。

## 長時間のセッションから見えた三つの問題

8月12日の`Harden tool contracts after long-running agent session`以降、履歴にはtool contractやroundtrip、非同期処理、複数エージェントの安全境界を修正するcommitが続きます。この時期の変更から、問題は大きく三つに整理できます。

### 1. ワークフローを細かく規定しても、現実の作業はその通り進まない

リポジトリを読む前に作った計画は、調査後には外れていることがあります。それでも固定されたplanやrunnerが手順の消化を重視すると、エージェントは成果物よりワークフローを完了させようとします。

必要だったのは強い手順ではなく、目標と受け入れ条件を保ちながら、観察に応じて計画を捨てられる状態管理でした。

### 2. モデルの報告と、実際に起きたことを区別できない

「テストに成功した」という文章と、ランタイムがテストコマンドを実行してexit code 0を得たことは同じではありません。子エージェントが「実装完了」と返した場合も、そのbranchが正しいとは限りません。

プロンプトで「必ず検証すること」と指示するだけでは、この区別はモデルの自己申告に戻ってしまいます。実行された証拠だけに完了権限を与える仕組みが必要でした。

### 3. ツールを分けすぎると、モデルへ内部事情を判断させることになる

BM25検索と構文検索は実装方式こそ違いますが、モデルの目的はどちらも「変更に必要な根拠を得ること」です。plan、grill、runner、loopも、モデルから見れば作業を進めるための近い概念でした。

内部実装の都合でtool surfaceを増やすと、モデルは本題に入る前にツールを選ばなければなりません。境界は実装方式ではなく、モデルへ与える権限で分けた方がよい、という整理になりました。

## 8月29日、機能の集合から「権限の境界」へ作り直した

転換点になったのが、8月29日の`refactor: rebuild Pi Kit around runtime boundaries`です。この変更では198ファイルに手が入り、約1,700行を追加する一方で約8,000行を削除しています。

ここで、Pi Kitを構成していた個別ワークフローの多くを取り払い、次の五つの境界へ組み直しました。

```text
リポジトリ ──> context ──> 調査結果
      │
      └──────> code ─────> 検証された変更

ユーザーの要求 ──> task ──> verify ──> task.finish
                       \
                        └──> delegate ──> 隔離された作業
```

この矢印は必須のパイプラインではなく、情報や権限がどちらへ流れるかを表しています。

たとえば、`context`は読み取り専用です。関連箇所をBM25で探すことも、Tree-sitterやLSPで宣言を探すこともできますが、リポジトリを変更する権限は持ちません。変更は`code`の役割です。

`task`は目標、受け入れ条件、観察、変更可能な計画を保持します。しかし、自分で完了を認めることはできません。`verify`が実際にテストや型チェックを実行し、その証拠がある場合だけ`task.finish`へ進めます。

`delegate`は子Piへ実装を任せられますが、親のworking treeを直接触らせません。子ごとにGit worktreeとbranchを作り、親が差分を確認してsquash mergeし、統合後にもう一度検証します。子の終了通知は作業イベントであって、採用の証拠ではないからです。

こうして見ると、五つのtoolは作業手順を一段ずつ表したものではありません。

- `context`：根拠を取得できるが、変更はできない
- `code`：対象を検証して変更できる
- `task`：目標と状態を保持できるが、完了は決められない
- `verify`：実行結果を証拠として記録できる
- `delegate`：作業を分離できるが、採用は決められない

Pi Kitが定義しているのは「次に何をするか」ではなく、「誰が、何を根拠に、どこまで決められるか」です。これがruntime boundaryという言葉の意味です。

## 一つの修正が完了するまで

現在の構成を、バグ修正の流れで見てみます。

まずエージェントはユーザーの要求を`task`へ置き、何が確認できれば終わりなのかを受け入れ条件にします。まだリポジトリを読んでいないため、この時点の計画は仮説です。

次に、場所が分からなければ`context`で関連コードを絞ります。概念から探すならBM25、宣言や呼び出しを探すならTree-sitterやLSPが内部で使われます。小さなファイルや場所が明らかな場合は普通に読めばよく、`context`の利用自体は義務ではありません。

対象が分かれば変更します。既存ソースの構文ノードを選べているなら`code`で編集し、新規ファイルや設定ファイルなら通常のファイル編集を使います。8月30日の`Reduce repository context-to-code friction`では、正確で一意な文字列が分かっている場合まで`context`のhandle取得を必須にするのは遠回りだと分かり、直接`code`へ渡せるようにしました。構造化編集を強制するのではなく、すでにある根拠を最短経路で使えるようにした変更です。

実装中に前提が外れていれば、`task`の計画を更新します。最初の計画を守ることより、現在の証拠に合わせることを優先します。

最後に`verify`で既存のテスト、compiler、typecheck、lintなどを実行します。レビュー結果やCIの報告も記録できますが、外部から報告された証拠だけでは`task.finish`できません。ランタイム自身が実行した強いcheckを最低一つ要求することで、完了の自己申告を防ぎます。

単純な修正なら、このすべてを使う必要はありません。読んで、編集して、既存テストを動かすだけで十分なこともあります。Pi Kitは一本道の儀式を強制するのではなく、危険がある場所だけに境界を置きます。

## 中核の外側にあるもの

`repository`、`task`、`delegate`が開発作業の権限を扱う一方、その外側には実行環境を扱うutilityがあります。

`terminal`はtmux上でTTY、標準入力、control key、起動完了を待つwatchを扱います。`background-process`は非対話のコマンドを別processとして実行します。似ていますが、ここでの分離は操作権限ではなく、プロセスとの対話方法が明確に異なるためです。

Web UIを変更した場合は`browser-inspector`でDOM、computed CSS、console、network、描画結果を確認できます。コード上のclass名が正しくても、実際のブラウザ表示が正しいとは限らないため、視覚的な変更には別の観測手段が要ります。

`session-metrics`は少し立場が違います。現在のセッションへ計測処理を差し込まず、Piが残したJSONLを後から解析します。toolの利用回数、error、token、cache、verification provenanceなどを見て、Pi Kitの変更が実際のセッションを改善したか判断するためにあります。

そしてskillは、extensionにするほど機械的ではない知識を担います。実装、障害調査、安全な操作、テスト設計、Git操作、文章作成などのskillを、その仕事に該当するときだけ読み込みます。以前のように安定した行動を`AGENTS.md`や常時注入するpromptへ積み上げず、必要な文脈だけを選ぶためです。

## 削ることも設計に含める

8月29日の再設計後も整理は続いています。使われなくなったUI extensionを削除し、statuslineとthemeのexportも外しました。9月6日には古い指示面を掃除しています。反対に、文章の修正や図解、不要な複雑さの削減など、runtimeで強制するものではない知識はskillとして追加しています。

この履歴から見えるのは、Pi Kitが完成したtool setを目指しているわけではないことです。実際のセッションで失敗を観察し、原因が機械的な境界の不足ならextensionへ、状況依存の判断ならskillへ置く。重複した境界や使われない機能は削る。その判断材料を`session-metrics`で再び集める、という循環を作ろうとしています。

```text
実際の作業
   ↓
session JSONL ──> session-metrics
   ↓
失敗や無駄を特定
   ↓
runtime boundary / skillを調整
   └────────────────> 次の作業
```

初期のPi Kitは「便利なextensionとskillのコレクション」でした。現在は、コーディングエージェントへどんな権限を渡し、どの判断には外部の証拠を要求するかを実験する、小さなruntime layerになっています。

## おわりに

Pi Kitは、モデルへ巨大な自律開発フレームワークを被せるものではありません。モデルは状況に応じて自由に調査し、実装できます。ただし、リポジトリを変更する、タスクを完了する、子エージェントの成果を採用するといった重要な地点では、モデル自身とは別の根拠を要求します。

プロンプトを工夫すれば一度はうまく動きます。しかし、長いセッションや異なるモデルでも同じ性質を保ちたいなら、文章だけでなくruntime側に責任を持たせる必要があります。Pi Kitの現在の構成は、短期間にツールを増やし、実際に使い、壊れた境界を直し、最後に大きく削った履歴からできています。

まだ変わると思います。むしろ、使っていない機能を残さず、実際の失敗に合わせて境界を引き直せることが、このプロジェクトで一番大事な部分です。
